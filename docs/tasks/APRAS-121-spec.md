# APRAS-121 — Make dependabot's uv runs regenerate requirements.txt with the lock

## The observed behaviour this task exists to correct

Dependabot's `uv` ecosystem does **not** regenerate the export. It edits
`backend/requirements.txt` as if it were a hand-maintained pip manifest,
bumping each pin to that package's own latest release, line by line,
independently of the resolution it writes into `backend/uv.lock`. The diff of
`cd8de18` (PR #47) shows exactly that shape: 25 single-line pin bumps inside a
file whose first two lines still claim `uv export` produced it, while the lock
moved to different versions. Line-by-line bumping has no resolver behind it,
which is why the result was not merely stale but uninstallable
(`pydantic==2.13.5` next to `pydantic-core==2.49.0`).

So regeneration is **this repository's own responsibility**. Nothing in
dependabot's uv support is going to start doing it, and `backend/requirements.txt`
is the install manifest for the Vercel backend deploy (`backend/vercel.json`
routes `/(.*)` to `index.py`), the one artifact no green CI job exercises.
Since APRAS-120 (`25e9dc6`) the drift is a red `Backend Tests` job, so every
grouped backend dependabot PR now stays red until its export is regenerated.

## Scope

Covers: a committed mechanism under `.github/` that regenerates the export from
the lock on a dependabot `uv` PR before review, a single committed definition of
the export command so the places that must agree can no longer diverge
silently, a CI check that the committed export is byte-identical to what that
command produces and resolves in a clean interpreter, a single pinned `uv`
version shared by every producer of the export, and a demonstration on a real
PR.

Does not cover: changing how Vercel installs (no `installCommand`, no dropping
`requirements.txt` in favour of the lock), the frontend `npm` ecosystem,
restating or reimplementing the parity assertions in
`backend/tests/test_requirements_export.py`, and any change to the repository
ruleset or to the list of required status checks.

## Operator prerequisite (blocks expected result 9 only)

The push in §2 needs a credential that an implementing agent cannot mint. The
operator must create, before result 9 can be demonstrated:

- a **fine-grained personal access token** owned by the repository maintainer
  (`heitor.polidoro@gmail.com`), scoped to this repository only, with the
  single permission **Contents: Read and write** and no other permission;
- stored as the **repository Actions secret `REQUIREMENTS_EXPORT_TOKEN`**
  (Actions secrets, *not* Dependabot secrets — `pull_request_target` runs in
  base context and reads the Actions list).

A GitHub App installation token is deliberately **not** chosen: with
`require_extra_approval_for_unattributed_changes: true` and a single
maintainer, a bot-authored commit can fall on the "unattributed" side of that
rule and demand a second approval nobody in this repository can give. The PAT
path avoids it because the commit is attributed to a real GitHub account — see
§2 for the author identity the push must set.

Results 1–8, 10 and 11 are fully implementable and verifiable without this
credential. Result 9 is the only one gated on it, and the task may be reviewed
and QA'd before the operator mints the secret — but result 9 carries its own
two-branch pass condition in its own text, so QA never needs this section to
tell *outstanding* from *unmet*.

**The mechanism does not exist until this lands on `master`.** A
`pull_request_target` workflow is taken from the *base* ref, so
`.github/workflows/requirements-export.yml` does nothing on the PR that
introduces it, and the base copy of `backend/scripts/export_requirements.sh`
(§2) does not exist either. Results 1–8, 10 and 11 therefore land on `master`
first, and result 9 is demonstrated afterwards against `master`.

## Behaviour

1. **One definition of the export command.** A committed script —
   `backend/scripts/export_requirements.sh` — is the only place the `uv export`
   invocation is written. Running it from a clean checkout rewrites
   `backend/requirements.txt`. The invocation **must** include `--frozen`
   (mandatory, not optional — see §2 for why it is a security requirement and
   not a preference): the export is produced from `uv.lock` as committed and may
   never re-resolve. `uv` writes the invocation it was given into the file's
   header comment, so the committed export must be regenerated by the script in
   this task (its header currently lacks `--frozen`); the header then agrees
   with the script by construction, and the CI check in §3 is what detects a
   hand edit. The existing test's failure message stops quoting the command and
   names the script instead.

   The script passes a **fixed argument list** — no conditional flags, no
   `--directory`, no values interpolated from the environment — so the header
   `uv` writes is independent of who invoked the script and from where. That is
   what makes result 2's "line 2 quotes the script's command exactly" and
   result 4's byte-for-byte claim hold anywhere rather than only on the machine
   that happened to run it.

   **One pinned producer.** The export's bytes (header, `# via` annotations,
   ordering, marker rendering) are `uv`-version artefacts, so a single uv
   version is pinned and every consumer of the script gets that one:

   - the pin's single source of truth is a literal near the top of
     `backend/scripts/export_requirements.sh` — `UV_PIN="0.12.19"` (the version
     in use locally today). The script compares it against `uv --version` and
     exits non-zero with a message naming `UV_PIN` and the version found,
     before exporting anything. This is the local story: a developer on another
     uv gets a refusal, never a differently-headed export. Reading `uv
     --version` is the only thing the check does; it reads no project file and
     resolves nothing.
   - `.github/workflows/requirements-export.yml` (§2) pins `setup-uv` with
     `version: "0.12.19"` and no `pyproject-file:`.
   - the `Backend Tests` block in `.github/workflows/ci.yml` (§3) gains
     `version: "0.12.19"` and **drops** `pyproject-file: backend/pyproject.toml`,
     so the asserting job and the producing job cannot install different uv
     builds. `enable-cache: false` stays. The other `setup-uv` uses in the
     repository are not touched — they do not run the script.

     Describe that removal accurately, because the current prose invites a
     wrong mental model: `pyproject-file:` is **not an input of
     `astral-sh/setup-uv@v8.1.0` at all** (the declared inputs are `version`
     and `version-file`). The three steps that pass it today are passing an
     undeclared input, which the action ignores while logging an
     unrecognised-input warning, so every `setup-uv` step in this repository is
     already installing **floating-latest uv**. Dropping it therefore costs
     nothing and silences a warning; it is not an override being removed.
   - the pin is deliberately **not** `[tool.uv] required-version` in
     `backend/pyproject.toml`: that file is head-controlled, and §2's rule is
     that no head file chooses the toolchain for the privileged job. Note the
     residual, and accept it: a head that *adds* `[tool.uv] required-version`
     incompatible with the pin makes `uv export --frozen` in the privileged job
     refuse to run. That is a fail-**closed** outcome — the job errors and
     pushes nothing — so it is not a security hole, and with the §2 observable
     in place it surfaces as a failed run rather than as silence.
   - the privileged job's `setup-uv` also pins `checksum:` for the uv
     `0.12.19` artefact it downloads. `setup-uv@v8.1.0` validates the download
     only against a caller-supplied checksum or its baked table, and that
     table — built when the action was tagged — has no entry for a later uv, in
     which case validation returns silently. Every other `setup-uv` step in the
     repository lives with that; this is the one job holding a push credential,
     so it does not.
   - **who bumps the pin.** Nothing bumps it automatically — dependabot does not
     update a `version:` string input — so a stale pin is safe but ages
     silently. The pin is bumped deliberately, by editing the three literals
     (and the `checksum:`) together in one commit; a red pin test means exactly
     that someone edited one of them alone.

   A test asserts the three literals agree: the `UV_PIN` value in the script
   and the `version:` value in each of the two workflow files are the same
   string. Its locator is named rather than left to taste, because this test is
   the pin's only backstop: it reads the `version:` input of the **`setup-uv`
   step of the `backend` job** in `ci.yml` — not any `version:`-suffixed key in
   the file, which would also match `node-version: 24` and the other two
   `setup-uv` blocks. Divergence is a red test, not a mysterious header diff.

   The "single definition" rule is enforced over `.github/workflows/`,
   `backend/tests/` and `AGENTS.md`: no file in those places may contain a
   `uv export` invocation of its own. Two exclusions are deliberate and must be
   written into the guard test:

   - `backend/requirements.txt` — `uv` itself writes the invocation into the
     generated header; that is the property §1 relies on, so the generated file
     is never scanned;
   - `docs/**` — specs, reviews and plans quote commands as prose by nature
     (this spec does), so documentation is out of the guard's reach.

   The needle is a **pattern, not the exact string**: `uv`, horizontal
   whitespace, `export`, matched **per line and with word boundaries on both
   sides** (`\buv[ \t]+export\b`). Both constraints are load-bearing: matched
   loosely across newlines, the pattern false-positives on an
   `astral-sh/setup-uv` reference followed by a shell `export FOO=…` line —
   which is plausible in exactly the two workflow files this task writes. The
   real header carries `--format requirements-txt --no-hashes -o
   requirements.txt`, §1's prose does not, and a future flag change must not
   silently disarm the guard. The guard test must **assemble that pattern from
   fragments at runtime** so that the test file itself contains no contiguous
   `uv export` literal — this, and not an `__file__` exclusion, is the chosen
   resolution, because it keeps the rule uniform instead of carving out the one
   file most likely to need it later. The needle matches only the `export`
   subcommand, so the `uv lock --check` step §3 adds to `Backend Tests` is
   outside it; `uv export --locked` would be inside it, which is why §3 rejects
   that form.

2. **Automatic regeneration on dependabot PRs.** A new workflow regenerates the
   export and, when the result differs from what is committed, pushes one commit
   onto the **PR branch** — never onto `master`; the ruleset targets
   `~DEFAULT_BRANCH` only and is not involved. Required behaviour:

   - It triggers on `pull_request_target` (opened, synchronize, reopened) for
     changes under `backend/`. `pull_request` is wrong here: a `pull_request`
     run on a dependabot PR gets a read-only `GITHUB_TOKEN` and no Actions
     secrets.
   - Its gate is the **branch name** (`dependabot/uv/` prefix on
     `github.head_ref`) plus `head.repo.full_name == github.repository`. It must
     *not* gate on `github.actor`, and nothing anywhere in the workflow may read
     `github.actor`, `github.event.pull_request.user` or
     `github.triggering_actor` — that is what makes a dependabot-shaped branch
     indistinguishable from dependabot's own, so the demonstration in §4
     exercises the identical path with nothing relaxed.
   - `permissions:` is `contents: write` and nothing else.
   - A `concurrency` group keyed on the PR number with
     `cancel-in-progress: true`, so a superseded head sha does not race its
     successor.

   **Which ref is checked out, and which code executes.** This is the
   load-bearing detail and the spec fixes it rather than leaving it to the
   implementer. Two rules, and they are not the same rule:

   - *Executed code comes from the base ref.* The workflow file itself is
     base-provided by GitHub under `pull_request_target`. The export script is
     not, because the PR can edit it — so the job must obtain
     `backend/scripts/export_requirements.sh` from
     `github.event.pull_request.base.sha` into a path **outside the work tree**
     and execute that copy. The head's copy of the script is never executed and
     never sourced. For the same reason the `uv` toolchain is pinned in the
     workflow by the literal `version: "0.12.19"` on `astral-sh/setup-uv`
     (§1's pin) and never by `pyproject-file:`, so no head-controlled file
     chooses the interpreter or the uv build.

     **The base copy must be fetched, not assumed present, and the form is
     fixed.** `actions/checkout` at an explicit sha fetches the history *of that
     commit*, so `git show <base.sha>:…` resolves only while `base.sha` is an
     ancestor of `head.sha` — true on a freshly opened PR, false as soon as
     `master` advances while the PR is open, including on the `synchronize` this
     workflow's own push fires. The job therefore runs, in the head work tree,
     an explicit

         git fetch --no-tags --depth=1 origin "$BASE_SHA"

     before reading the script with `git show "$BASE_SHA":backend/scripts/export_requirements.sh`.
     Nothing in the step may rely on the head checkout's history already
     containing `$BASE_SHA`.

     **A second `actions/checkout` is not an acceptable alternative here, and
     the reason is mechanical.** `actions/checkout`'s `path:` is interpreted
     relative to `$GITHUB_WORKSPACE` and the action refuses a value resolving
     outside it, so with the head checked out at the workspace root there is no
     legal `path:` that lands *outside* the head work tree. Making one would
     mean relocating the head into its own `path:` as well, which moves every
     other path in the job — the `cd backend` the shared script performs, the
     push's work tree — for no gain; and keeping the head at the root makes the
     checkout *order* silently load-bearing, because `actions/checkout` runs
     `git clean -ffdx` on its target and a base checkout written first is
     deleted by the head checkout that follows. The `git fetch` form has
     neither hazard.

     That form works **because this repository is public**: an unauthenticated
     fetch-by-sha from `origin` succeeds even though both checkouts use
     `persist-credentials: false`. Record that dependency — if the repository
     ever becomes private this step must be revisited, and it will fail loudly
     (see the next paragraph) rather than quietly doing nothing.

     **The job must be distinguishable from a job that never ran.** This is the
     failure mode the task keeps reproducing: the workflow silently does
     nothing, and "ran and found nothing to do" looks identical to "never
     triggered". So the job's final step **always** writes one line to
     `$GITHUB_STEP_SUMMARY`, on every path it can reach, naming the base sha it
     fetched and exactly one of two outcomes — `export regenerated; pushed
     <sha>` or `export already matches the lock; nothing to push`. A run that
     found nothing to do therefore still leaves a visible run with a summary
     line; the absence of any run for the head sha means the trigger, the gate
     or the `paths:` filter rejected it, and the two can no longer be
     confused. Every failure path described in this section (missing base
     script, absent secret) fails the job rather than exiting zero.

     If the base sha has no `backend/scripts/export_requirements.sh` — the
     state of `master` until this task lands — the job fails with a message
     naming that path and saying the mechanism is not yet on the base branch,
     not with a bare `git`/`cp` error.

     The copy is placed at `"$RUNNER_TEMP/export_requirements.sh"` and invoked
     as `bash "$RUNNER_TEMP/export_requirements.sh"` (an absolute path after an
     explicit `chmod +x` is equally acceptable), so nothing resolves the script
     name through `PATH` or the work tree and nothing depends on an exec bit
     surviving the copy.
   - *Only head **data** enters the export.* The work tree is the head sha
     (`ref: github.event.pull_request.head.sha`, `persist-credentials: false`),
     because the commit being pushed must sit on top of the PR's own tree.
     `backend/uv.lock` and `backend/pyproject.toml` are therefore the head's —
     read as data by `uv export --frozen`, never executed.
   - *No caching, in either direction.* A `pull_request_target` run executes in
     base context, so anything it saves lands in the **base-branch cache
     scope** that `master`'s own runs restore, under a key influenced by the
     head's `uv.lock` — a write path from a PR branch into `master`'s CI
     inputs, which "executes no PR code" does not cover. The workflow therefore
     passes `enable-cache: false` to `setup-uv` (as every other `setup-uv` in
     this repository does) and contains **no `actions/cache` step** and no
     other cache action.

   **Why `--frozen` is mandatory here.** A non-frozen `uv export` is permitted
   to re-resolve, which means reading head-controlled `pyproject.toml` and,
   for any dependency whose metadata comes from a source distribution,
   invoking a **head-controlled build backend** — arbitrary code execution in a
   job holding a Contents:write push credential. The §2 gates restrict who can
   create such a branch to accounts that already have push access; that is a
   real mitigation, not a substitute for the job's own requirement that it
   execute no PR code. The weight of that requirement is specific here: ruleset
   `16257354` grants the admin repository role `bypass_mode: always`, so the
   maintainer-owned PAT this job holds can push to `master` past all nine
   required checks — code execution in *any* step of this job is a `master`
   compromise, not merely a tampered PR branch.

   `uv export --frozen` is the metadata-free path: it reads the lock and
   resolves nothing. So the privileged job runs **nothing else that could need
   project metadata**. In particular it carries **no lock-freshness
   assertion**: `uv lock --check` must read `pyproject.toml`, and a head may
   declare `dynamic = ["dependencies"]`, a `[tool.uv.sources]` path entry or a
   `[build-system]` with an in-tree `backend-path`, any of which makes uv obtain
   metadata through a PEP 517 backend out of the head tree. The freshness check
   therefore lives in `Backend Tests` (§3) instead, which runs with a read-only
   token and no secrets.

   The consequence is deliberate and benign: on a stale head lock this job
   produces the export that matches that lock and pushes it, and the stale lock
   itself is then reported by `uv lock --check` in `Backend Tests` on the PR —
   the same place every other lock problem surfaces. It is not reported by the
   job holding the push credential.

   The job never runs `uv lock` in any form, never runs `uv sync`, installs
   nothing, runs no tests, and exposes no secret other than the push token. Its
   only `uv` invocation is the one inside the base-ref script.

   **The push.** It must re-trigger the required status checks on the new head
   sha. A `GITHUB_TOKEN` push does not trigger workflows, and
   `strict_required_status_checks_policy` is `true`, so that choice leaves the
   PR permanently unmergeable with missing checks. The push therefore uses
   `secrets.REQUIREMENTS_EXPORT_TOKEN` (the operator-provisioned fine-grained
   PAT above), referenced **only** in the env of the push step — no other step
   may see it. Commit author and committer are both the maintainer's GitHub
   identity (`Heitor Polidoro <heitor.polidoro@gmail.com>`), so the commit is
   attributed to a GitHub account and the
   `require_extra_approval_for_unattributed_changes` rule is not engaged. The
   commit contains **only** `backend/requirements.txt`.

   The refspec is written out, because the work tree is a **detached head** at
   `head.sha` and — with `fetch-depth: 1` plus the `--depth=1` base fetch —
   **shallow**: the push is `git push origin HEAD:refs/heads/"$HEAD_REF"` with
   `$HEAD_REF` from `github.head_ref`. A bare `git push` has no upstream to
   resolve and `git push origin HEAD` would target `refs/heads/HEAD`.

   If the secret is
   absent or empty the job fails with an explicit message naming it — it must
   not skip silently. Its presence must be verified on the demo PR, not
   assumed: this project already learned from `SONAR_TOKEN` that a
   dependabot-context run sees only the separate *Dependabot secrets* list.

   **Termination.** When the regenerated export is byte-identical to the
   committed one the job commits nothing and pushes nothing — it is a no-op.
   That is precisely what makes the `synchronize` event fired by its own push
   terminate: the second run regenerates, finds no difference, and stops.

   **One side effect to expect.** Dependabot stops force-pushing a branch it
   sees as modified by another author, so after this job's push dependabot will
   no longer rebase or re-drive that PR. That is harmless for this repository's
   habit — a grouped backend PR is reviewed and merged, not re-driven — but it
   means a PR left open long enough to go stale must be closed and let
   dependabot reopen it rather than waiting for a rebase that will not come.
   Nothing here interferes with dependabot's *other* updates.

3. **CI proves the committed export was generated, and installs.** The existing
   `Backend Tests` job in `.github/workflows/ci.yml` (`uv` already installed
   there) has its `setup-uv` block pinned per §1 (`version: "0.12.19"`,
   `pyproject-file:` removed, `enable-cache: false` kept) and gains three
   steps:

   - **`uv lock --check`**, run from `backend/`, asserting the committed lock is
     fresh with respect to `pyproject.toml`. This is the assertion §2 keeps out
     of the privileged job; `uv lock --check` is the chosen form and the
     `uv export --locked` variant is **rejected**, because any `uv` +
     whitespace + `export` text in a workflow file is exactly what §1's guard
     and result 6(b) forbid. Here the token is read-only and no secret is
     exposed, so reading head-controlled `pyproject.toml` costs nothing.
   - run the script and assert `git diff --exit-code -- backend/requirements.txt`;
   - create a throwaway interpreter and dry-run the export against it:
     `uv venv --python 3.13 "$RUNNER_TEMP/export-check"` followed by
     `uv pip install --dry-run --python "$RUNNER_TEMP/export-check" -r
     backend/requirements.txt`. The isolation is the point and resolves the
     ambiguity in the old wording: by the time this step runs,
     `uv sync --all-groups` has populated `backend/.venv` with the lock's full
     contents, and a dry-run against *that* venv would be a materially weaker,
     differently-behaving check. The dry-run must not use `backend/.venv`.
     `--python 3.13` is written out explicitly and never left to be inherited
     from `backend/.python-version`, so the interpreter the check uses is
     readable in the workflow and does not change when that file does.

   **What this adds over APRAS-120's test.** `test_requirements_export.py`
   already asserts bidirectional *pin-level* parity against `uv.lock`, offline;
   the regenerate-and-diff step adds the **byte-level** properties that test
   cannot see — the generated header, line ordering and environment markers —
   and the dry-run adds installability, which no pin comparison establishes.
   Neither step is redundant with the test and neither should be removed as
   such.

   **Step order.** All three steps go **before** the 30-minute wrapped pytest
   step, in the order above. They cost seconds to a minute, and placed first
   they still report their verdict when the known `Backend Tests` hang recurs.
   APRAS-119 also changes this job; whichever lands second keeps these steps
   ahead of the pytest step rather than reordering them.

   **Network dependency.** The dry-run resolves against PyPI, and that
   dependency is **accepted** — installability cannot be checked offline. To
   keep a PyPI blip from becoming a red required check with no code cause, the
   dry-run step retries once after a short sleep; a second consecutive failure
   is a real failure and must not be retried further or made
   `continue-on-error`.

   All three steps go in the existing job: no new status-check context is
   introduced, so the ruleset's required list is untouched.

4. **Demonstration, on a PR.** A quoted workflow file or a screenshot does not
   discharge this. Either a real open dependabot PR or, failing one, a
   *dependabot-shaped* PR: head branch in the same repository named
   `dependabot/uv/backend/<anything>`, targeting `master`, whose single commit
   changes `backend/uv.lock` **and** `backend/requirements.txt` so that the
   export disagrees with the lock in the way `cd8de18` did — at least one pin
   above its locked version, and at least one pin pair the resolver rejects.
   The commit must touch `backend/**` so the workflow's `paths:` filter admits
   it (it does, by construction).

   **How each of the two files is produced matters.** `backend/uv.lock` must be
   the output of a real `uv lock` / `uv lock --upgrade` — never hand-edited —
   because result 9 requires `Backend Tests` to reach `success` on the pushed
   sha, and §3's `uv lock --check` rejects a hand-edited lock. Only
   `backend/requirements.txt` is hand-edited, with line-by-line pin bumps
   mimicking `cd8de18`. A `uv lock --upgrade` run produces the first property
   for free (locked versions move, the hand-written pins do not follow), and the
   unsatisfiable pair is introduced by hand in the export alone. A failed demo
   must be diagnosable as the mechanism failing, not as a lock the repository's
   own gate would have rejected anyway.

   Recorded on the task: PR URL, the workflow run id that regenerated the
   export, the sha of the pushed commit, and `Backend Tests` at
   `conclusion: success` on that sha. Because `dismiss_stale_reviews_on_push`
   is `true` and `require_extra_approval_for_unattributed_changes` is `true`,
   the record must also state the PR's mergeability after the bot push with one
   approval.

   The demonstration PR is then **closed and its branch deleted — never
   merged**: its committed export is deliberately unsatisfiable, and merging it
   would land exactly the breakage this task exists to prevent.

5. **Two documentation corrections.** `.github/dependabot.yml`'s comment claims
   the `uv` ecosystem "updates `pyproject.toml`, `uv.lock` and the export
   together" — it edits the export without regenerating it; correct the comment
   and name the workflow that does the regeneration. `AGENTS.md` gains one
   line: the export is never hand-edited, and
   `backend/scripts/export_requirements.sh` is the only way to regenerate it.
   Neither may spell out a `uv export` invocation (§1).

## Decision on the `dev` group

**Declined: the export keeps shipping the `dev` group**, and the reason is
recorded here rather than left implicit. `--no-dev` would drop `pytest`,
`pytest-cov`, `pytest-timeout`, `coverage`, `ruff` and `zxing-cpp` from the
Vercel install — a build-time saving only; no application import was found for
any of them. Against that,
`test_requirements_export.py::test_every_locked_package_is_pinned_in_the_export`
derives its expectation from the whole lock, and a `--no-dev` export would
require it to compute the dev-only closure from `uv.lock` — a marker-aware
reachability walk, i.e. a small resolver — or to shell out to `uv`, which
cannot be made conditional because `backend/scripts/assert_no_skips.py` forbids
skips. Weakening the offline gate that runs everywhere, in order to save six
packages of install time, is the wrong trade for this task. Worth revisiting as
its own task once a deploy-side check exists that would notice a missing
runtime dependency.
