APRAS-68 — Cores da marca do condomínio

Nova seção em Sistema → Perfil do condomínio (/admin/tenant-profile), sob a permissão existente tenants:profile_update. Escreve tenant.brand_theme (coluna JSON) via PATCH /api/v1/tenant-profile; a resposta traz o theme derivado.

Dois modos. No Simples o condomínio escolhe duas cores e o resto — inclusive o modo escuro — é derivado, com contraste garantido por construção. No Avançado o condomínio escreve a paleta inteira, e aí qualquer par de texto/fundo abaixo de 4,5:1 é recusado (não apenas avisado). A recusa vale na API, não só na tela.

Onde cada cor aparece. A primária vai para --primary e --ring (botões principais, links, foco). A cor de destaque vai para --secondary em croma cheio — os botões secundários (“Depois”, “Cancelar”) — e não para --accent, que continua sendo só um tom pálido de fundo de hover (hover:bg-accent). Sem isso a segunda cor viraria um quase-branco imperceptível.

Cores da marca

O servidor é o juiz: a derivação e a medição de contraste vivem em app/core/branding.py.

Duas cores. Fundos, textos, bordas e o bloco .dark inteiro são derivados em OKLCH — o contraste não pode falhar porque o sistema escolhe os dois lados de cada par.

Formato #rrggbb, maiúsculas ou minúsculas — o servidor normaliza para minúsculas.

Divulgação honesta: --accent é derivado só do matiz do destaque, com croma de ~1% — toda a faixa emitida vai de #e3f6f5 a #ffeee8, ou seja, quase-brancos. É de propósito (é superfície de hover). A cor que a pessoa realmente vê é --secondary: #0ea5e9 emite oklch(0.68 0.14 237.32) ≈ #23a3e3, com texto a 6,96:1.

Você escolhe os dois lados de cada par, então a garantia automática deixa de existir. Combinações abaixo de 4,5:1 são recusadas — o salvamento fica bloqueado e a API devolve 422.

PATCH /api/v1/tenant-profile

Estas cores não podem ser salvas

2 combinação(ões) abaixo do mínimo legível de 4,5:1 (WCAG 2.1 AA, texto normal). Ajuste as cores destacadas abaixo. Se a requisição for enviada por fora da tela, a API responde 422 com a mesma lista. 

{

    {"pair": "card-foreground/card",       "ratio": 1.10, "minimum": 4.5},
    {"pair": "primary-foreground/primary", "ratio": 1.26, "minimum": 4.5}

Todos os pares medidos passam de 4,5:1. Medição feita sobre o valor já arredondado a 2 casas e já encaixado no gamut sRGB (croma reduzido na grade de 0,01 até caber) — isto é, exatamente a cor que o navegador pinta, não só a string que ele recebe.
Qual lado o reparo move, por par. --primary, --secondary e --accent (lado não-texto) se afastam do seu primeiro plano; --muted-foreground (lado texto) desce no claro e sobe no escuro até passar nas três superfícies contra as quais é medido (--muted, --background, --card), porque essas três não podem se mexer. foreground/background e card-foreground/card nunca precisam de reparo.

{"mode": "simple",   "primary": "#7c3aed", "accent": "#0ea5e9"}
{"mode": "advanced", "light": { /* 13 chaves */ }, "dark": null }

      
Medição: arredonda a 2 casas → reduz o croma até caber no gamut sRGB → só então mede.
        A CSS Color 4 §13 manda o navegador mapear o croma de uma oklch() fora do gamut; medir o
        recorte ingênuo certificaria pares que o navegador pinta abaixo de 4,5:1 (pior caso medido:
        oklch(0.52 0.22 210) sobre oklch(0.15 0.02 210), medido 4,52 e pintado 3,74).

      
Derivação: uma só, em app/core/branding.build_theme(tenant.brand_theme).
        A APRAS-74 (endpoint público /c/<slug>) chama a mesma função; não existe porte em TypeScript.
        O front leva apenas a função de razão de contraste, pinada contra
        backend/tests/data/contrast_fixtures.json pelos dois lados.

      
Nunca sobrescritas: --destructive*, os 10 tokens de status,
        os 8 de prioridade e --radius* — são semânticos e iguais em todo condomínio.
